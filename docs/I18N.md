# Internationalization and localized routing

## Source of translations

Static translatable copy lives only in `public/i18n/en.json` and `public/i18n/es.json`. Keys are semantic paths grouped by concern, such as `accessibility.skipToContent`, `errors.notFound.title` and `seo.home.description`. Components, templates and SEO helpers consume `TranslationService`; they never import dictionaries or know their paths.

The service imports the JSON files at build time. Angular embeds the same dictionaries in browser and server bundles, so translations are synchronously available during SSR without an internal HTTP request. Hydration starts with the same URL, dictionary and rendered strings: there is no translation request, language flash, second render or transfer-cache dependency. If dictionaries later split by feature, only the service loading strategy changes.

## Locale and navigation

The URL is authoritative. Public prefixes are `/en` and `/es`; internal formatting locales are `en-US` and `es-US`. `TranslationService` derives its locale from the initial router URL and updates it at navigation start, then confirms the post-redirect URL at navigation end. It never consults localStorage or browser language.

`RouteId` provides stable route identities and `buildLocalizedPath` maps them to localized segments. Entity routes require a localized slug. Language switching therefore remains route identity + entity identity + target locale; changing a dictionary without changing the URL is not a supported language switch.

`resolveEntityLocalePath` implements this boundary for content. Given one entity ID and localized slugs, `/en/projects/ocean-residence` resolves to `/es/proyectos/residencia-oceano`. Missing draft slugs return `null`, allowing UI to omit an unavailable alternative rather than navigate incorrectly.

## Typing, parity and fallback

`TranslationKey` is derived from the English JSON tree, so template and TypeScript calls are checked against known leaf keys. The parity test flattens both JSON trees and requires identical keys and non-empty string values. It runs with `npm test` and fails CI for missing or extra translations.

If runtime lookup still fails, development logs `Missing translation: <key> (<locale>)` and tries English. Production uses the same safe English fallback without exposing the internal key. If English is also absent, the service returns an empty string rather than leaking an implementation identifier.

## SEO and future CMS content

Static SEO copy uses keys under `seo`. Each indexable locale still has its own canonical plus reciprocal `en`, `es` and `x-default` links. Future dynamic copy, localized slugs and SEO fields will come from the CMS entity translation selected by URL locale; they will not be copied into the static dictionaries.

No third-party i18n library or XLIFF/build-per-locale strategy is used.
